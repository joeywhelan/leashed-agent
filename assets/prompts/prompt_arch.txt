# Summary

The request presents a detailed specification for creating an architecture diagram for a demo in which a human and an AI coding agent use the same Elastic CLI against the same Elastic Cloud Serverless project, and three independent permission layers keep the agent on a leash.

**Primary Focus:** Visualize two paths to one index. A Jupyter notebook, standing in for the human operator, drives everything: it provisions the project, loads a product catalog with planted data-quality defects, explores it by hand, and then launches Claude Code headless to audit the catalog and fix what it can. Both the notebook and the agent invoke the single `elastic` binary, which reads one config file holding three contexts. The human's path runs through the `admin` context and reaches the index directly. The agent's path runs through the `agent` context and must pass three gates in sequence: Claude Code's tool permission, the CLI's command allowlist, and a read-only Elasticsearch API key. The diagram must make those three gates structurally obvious as stages on the agent's path that the human's path does not cross, and must show that both paths end at the same `products` index.

**Key Structural Elements:**
- Jupyter notebook (`demo.ipynb`, Bash kernel) as the client and driver at the top of the diagram. It is the human. It holds the `--use-context admin` path and it launches the agent
- Claude Code (`claude -p`, model `claude-sonnet-5`) as a distinct node beside and slightly below the notebook, launched by it, returning a transcript and a report to it
- Elastic CLI (`elastic`) as one node in the visual middle that both actors call. Attached to it, a small config node: `out/elasticrc.yml` with three contexts listed inside it: `cloud`, `admin`, `agent`. The CLI is the only thing that touches the config
- The three gates drawn as **three stacked horizontal bands** across the agent's path only, numbered as the demo numbers them, from the index outward — this is the centrepiece and should occupy the visual middle-right of the frame:
  1. `Layer 1: Elasticsearch API key` — sits on the Serverless boundary where the agent's path enters it; carries the note `read, view_index_metadata, monitor on products*`; refuses with `403`
  2. `Layer 2: CLI allowlist` — sits inside the Elastic CLI node on the agent side; carries the note `commands.allowed: reads + ES|QL`; refuses with `command_blocked`
  3. `Layer 3: Claude Code tool permission` — sits between Claude Code and the Elastic CLI; carries the note `Bash(elastic *) only / deny --use-context, --config-file`; refuses with `denied`
  The agent's path meets them in the order 3, 2, 1 as it travels toward the index. The human's path from the notebook to the CLI and on to the index passes beside all three bands and crosses none of them
- Elastic Cloud Serverless project (`aws-us-east-1`, general purpose) as a dashed boundary box containing everything Elastic-managed: the `products` index and the Cloud API node
- `products` index (5,040 documents) with fields `sku` (keyword), `category` (keyword), `price` (double), `name` (text + keyword); planted defects are not depicted
- Cloud API as a small node inside the boundary, reached from the CLI's `cloud` context, used once to create the project and once to delete it
- `assets/data/gen_products.py` and `assets/data/products.ndjson` as the data source at the bottom left; `out/transcript.jsonl` and `out/report.md` as the agent's outputs at the bottom right; `.env` as a small muted node feeding the Cloud API key into the CLI config

**Canvas and Sizing — the image is embedded in a GitHub README:** 1600 × 1000 px (16:10), delivered as a PNG file (not JPEG or WEBP), opaque, saved to `assets/images/arch.png`, under 1 MB. GitHub does not crop README images; it scales them to the width of the content column while preserving the aspect ratio. That column measures about 830 px on a desktop repository page and shrinks with the window on smaller screens and mobile, so this canvas is a 2× asset that will display at roughly 830 × 520 px on desktop and smaller elsewhere. Design for that display size, not the pixel size: every label must remain legible at half scale, so the smallest text in the frame is no smaller than 24 px on the 1600-px canvas, node titles are at least 36 px, and arrow labels are at least 28 px. Prefer fewer, larger labels over dense small ones. Keep at least 3% clear margin on every edge. The background must be opaque, not transparent: GitHub renders the README on a white page in light mode and a near-black page in dark mode, and an opaque dark canvas reads the same on both without needing separate light and dark variants.
