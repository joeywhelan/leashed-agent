Least Privilege for AI Agents, with the Elastic CLI

Three permission layers give an AI agent exactly the Elasticsearch access its task needs, and the Elastic CLI is where you set them.

A live demo: a human and an agent share one CLI against one Serverless project

The question

An agent is only useful with real access. How much is the right amount?

  • Today the answer is usually all or nothing. The agent gets a service account with broad rights, or it gets a chat window and no hands.
  • Least privilege is the standing answer for people and services. Grant what the task needs, enforce it where it cannot be argued with, keep the record. Agents should get the same treatment.
  • The Elastic CLI is where that happens. One binary for Elasticsearch, Kibana and Cloud, the same for a person and for an agent, with a per-context policy that says which commands may run.

What you get

  • One tool for people and agents. Nothing built or maintained separately for automation.
  • Access is a policy setting, not a code change. A few lines of commands.allowed on a context.
  • Credentials never enter the model. The CLI resolves secrets from its config; the agent never sees a key.
  • Every action is a readable record. The agent's work is literal elastic commands.

The demo

Two paths to one index: the human's runs straight through, the agent's crosses three gates

  • Scenario. A product catalog with planted data-quality defects. The human loads and explores it; the agent is asked to audit it and fix what it can.
  • One config file, three contexts. cloud for the Cloud API, admin for the human, agent for the agent. The human types --use-context admin; the agent gets the default.
  • Everything is a shell cell. A Bash-kernel notebook runs elastic, claude -p and jq. No SDK, no wrapper code.
  • Clean start, clean finish. The project is created in the first section and deleted in the last. Your own CLI config is never touched.

The human, part one

Provision a project and load a catalog, all from the CLI

  • One command creates the project and, with --save-as admin, writes its endpoint and credentials into a context. Credentials are redacted in the output by default.
  • The config lives in out/, selected with ELASTIC_CLI_CONFIG_FILE. Teardown deletes it with everything else.
  • helpers bulk-ingest loads 5,040 documents with batching and retries in about two seconds.

The human, part two

The defects are visible from the shell to anyone who looks

elastic es esql query --use-context admin --format tsv \
  --query "FROM products
           | STATS docs = COUNT(*) BY category | SORT docs DESC"

elastic es search --index products --use-context admin --size 0 \
  --query '{"bool":{"must_not":{"exists":{"field":"price"}}}}' \
  --output-template "{{ hits.total.value }} products have no price"
→ 30 products have no price
  • ES|QL straight from the shell, with --format tsv for a table you can read.
  • Shape the output in the command. --output-fields keeps only the paths you name; --output-template turns one value into a sentence. No jq layer.
  • Six categories should come back. Eighteen do. The catalog needs a proper audit, and that is the agent's job.

Leash the agent

One delete, refused three times, by three different parties

1ElasticsearchA read-only API key on the agent context: read, view_index_metadata, monitor on products*403 from the server
2The elastic binarycommands.allowed on the agent context: reads and ES|QL only. Checked before any request is sentcommand_blocked, exit 1

Get past one and the next is waiting. The agent only ever meets the first; the notebook proves all three.

What the leash looks like

Three small files. Widening the agent from audit to repair is a config edit.

Layer 1 · agent-key.json

{ "name": "leashed-agent-agent",
  "role_descriptors": { "products_read_only": {
    "cluster": ["monitor"],
    "indices": [{ "names": ["products*"],
      "privileges": ["read", "view_index_metadata",
                     "monitor"] }] } } }

Layer 3 · the claude command line

claude -p "$(cat assets/prompts/audit.md)" \
  --tools Bash --allowedTools "Bash(elastic *)" \
  --disallowedTools "Bash(elastic * --use-context *)" \
                    "Bash(elastic * --config-file *)" \
  --model claude-sonnet-5 --max-turns 30

Layer 2 · agent-policy.yml

allowed:
  - version
  - status
  - stack.es.info
  - stack.es.count
  - stack.es.search
  - stack.es.esql.*
  - stack.es.indices.get-mapping
  - stack.es.indices.get-settings
  - stack.es.helpers.scroll-search
  # ... 15 more reads; nothing that writes
  • Attached to the context with one yq line; a context's list replaces the root list.
  • To let the agent apply fixes itself, add stack.es.update-by-query and re-mint the key with write. Nothing else changes.

The agent

Asked to fix what it can, it finds everything, hits the wall once, and hands back commands

  • The task is plain language: audit products, fix what can be fixed mechanically, report. It is not told its context is read-only.
  • It finds all five defect classes with ES|QL, with counts that match the plant exactly, and three examples each.
  • It checks --help, then tries update-by-query. The CLI answers command_blocked. It does not retry or look for another route.
  • The report is the deliverable: what it changed (nothing), proposed commands for the operator, and what needs a human decision and why.

The human, part three

Check the receipts, turn the keys, two defect classes go to zero

  • Two receipts before acting, pulled from the transcript with jq: the wall the agent hit, and zero credential strings anywhere in the record.
  • Two update-by-query calls with --use-context admin, the one thing the agent could not do: lowercase every category, trim every name.
  • 150 → 0 and 60 → 0. The category breakdown is back to six rows.
  • Three classes are left on purpose. Duplicates need a keep-or-drop decision per pair; missing and negative prices have no source of truth in the index. That is a data owner's call, not an agent's.

  • Read-only was this demo's setting, not the point. The allowlist is a dial. Many teams will want the agent to apply the mechanical fixes itself, and that is a policy edit reviewed like any other change.
  • The agent reasons; the human decides. It found every defect and wrote the exact commands. The judgment calls stayed with the person holding the keys.
  • Agents read CLAUDE.md. Ground rules such as "confirm flags with --help" and "a refusal is final" shaped a report the operator could run as-is.
